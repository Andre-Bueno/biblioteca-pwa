## Resumo
O IP do cliente usado por rate limit e lockout vem so de `request.client` (apos o uvicorn). Se o IP do proxy nao estiver em `FORWARDED_ALLOW_IPS`, todos os usuarios viram um unico "IP" (o do proxy), e 20 logins errados de qualquer pessoa bloqueiam o login de todos (e 20 req/min no limite de auth e compartilhado). O padrao documentado (`172.17.0.1`) e o gateway da bridge padrao do Docker, mas o compose cria a rede de projeto `infra_default`, cujo gateway e outro.

## Como reproduzir
Comprovado (comportamento do app quando o IP do proxy nao e confiavel, simulado localmente):
1. Subir o app com `FORWARDED_ALLOW_IPS=172.17.0.1` (conexoes de 127.0.0.1 nao sao confiaveis, como um proxy "nao listado") e limites padrao, porta 18701.
2. Enviar 14 `GET /api/v1/auth/csrf` com `X-Forwarded-For`, `X-Real-IP` e `Forwarded` diferentes em cada um.
3. Observado: `[204 x10, 429 x4]`. Os cabecalhos sao ignorados e todos dividem o mesmo balde (burst 10).
4. Num app que ve um unico IP (instancia 18703): 20 logins errados com 20 usernames diferentes e depois login correto de qualquer conta nesse IP: `429` (`Retry-After: 300`, dobrando ate 3600 s). Saida: `legit victim creds from sprayer ip: 429`.

Verificacao estatica da causa (nao foi possivel subir Docker: daemon indisponivel na maquina de auditoria):
`docker compose -f infra/compose.example.yml config` mostra `networks: default: name: infra_default` (rede implicita, nao a `bridge`). O gateway de `infra_default` e alocado pelo Docker (ex.: `172.18.0.1`), nao `172.17.0.1`. A porta e publicada em `127.0.0.1`; um proxy no host chega ao container pelo gateway da rede do projeto.

## Evidencia
- `infra/compose.example.yml:12` `FORWARDED_ALLOW_IPS: ${FORWARDED_ALLOW_IPS:-172.17.0.1}` e nenhum bloco `networks:` com subnet/gateway fixos.
- `infra/Dockerfile:20` `ENV FORWARDED_ALLOW_IPS=127.0.0.1` (diverge do compose; ja listado como M-3 no SECURITY_MAP).
- `backend/app/api/http_utils.py:36-40` `client_ip` usa so `scope["client"]`; sem aviso quando todos os clientes chegam do mesmo IP.
- `backend/app/services/auth_service.py:316-321` o escopo `ip` bloqueia a conta de login inteira daquele IP; `ip_policy` = 20 falhas / 15 min, lock 300 s ate 3600 s.
- Logs do app nao indicam o problema (nenhum aviso de "IP unico").

## Impacto
Qualquer anonimo faz DoS do login para todos os usuarios com ~20 requisicoes por hora (e o limite de 20 req/min/auth e comum a todos). Pre-condicao: deploy com o padrao do compose atras de proxy no host (cenario documentado) onde o IP do proxy nao bate com o valor configurado. O mesmo vale para o Dockerfile usado sem compose. Tambem anula a protecao por IP (um atacante legitimo e todos os usuarios sao um so).

## Correcao recomendada
1. No compose, fixar a rede (`networks: default: ipam: config: [{subnet: 172.28.0.0/24, gateway: 172.28.0.1}]`) e usar esse gateway/CIDR como padrao de `FORWARDED_ALLOW_IPS`; ou documentar o comando exato para descobri-lo e exigir a variavel (sem padrao enganoso).
2. Remover o `ENV FORWARDED_ALLOW_IPS=127.0.0.1` do Dockerfile (ou alinhar), para nao haver dois padroes.
3. Defesa em profundidade no app: log de aviso no startup/no primeiro login quando o IP visto for privado e constante (ou contador de IPs distintos baixo) e, opcionalmente, limite de lockout por IP mais alto quando nao houver proxy confiavel configurado.
