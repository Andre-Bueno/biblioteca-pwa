## Resumo
`read_page` e `read_cover` chamam `_pages()`, que abre e le o cabecalho de TODA imagem do CBZ a cada requisicao (para validar magic bytes e ordenar). Em arquivos grandes isso consome CPU proporcional ao numero de entradas por requisicao; qualquer usuario autenticado pode saturar o processo. O corpo da pagina (ate 64 MiB) tambem e lido inteiro na memoria.

## Como reproduzir
Instancia local (`docs/security/poc/page_cpu.py` cria um CBZ com 9500 PNGs de 76 bytes, dentro do limite de 10000 entradas):
1. Admin faz scan; usuario comum pede `GET /api/v1/items/<id>/pages/0` do item "manyentries9k".
2. Observado: 174 ms para uma pagina de 76 bytes (CBZ normal com 3 paginas: 4,6 ms).
3. Concorrencia (GIL/CPU): 16 requisicoes em 8 threads = 7,4 s no total, mediana 3,5 s por requisicao; 32 em 16 threads = 15,4 s, mediana 7,3 s. Vazao ~4,4 req/s independente de threads.
4. `bigpage.cbz` (pagina de 60 MiB, valida): resposta de 62.914.636 bytes em ~170 ms; 16 em paralelo = 1,7 s (todas em memoria no servidor, sem streaming).
O limite global por IP (600/min, burst 200) permite ~10 req/s, acima da vazao de ~4,4 req/s: um unico usuario basta.

## Evidencia
- `cbz.py:100-111` `_pages`: `for info in candidates: with zf.open(info) ... sniff_image(member.read(HEADER_BYTES))` para todas as entradas; `cbz.py:120-123` `read_page` sempre reconstroi a lista.
- `items.py:113-134` nenhuma limitacao de concorrencia nas rotas de pagina/capa; `Container.extractors` sem cache de indice.
- `pages.py:24-30` usa `item.page_count` (do scan) so para validar o indice, mas o extrator refaz o trabalho completo.

## Impacto
DoS autenticado e barato (qualquer conta do app) contra a unica instancia (estado em memoria, uma worker). Pre-condicao: existir CBZ com muitas entradas na biblioteca (entradas validas, nao hostis; o limite de 10 000 entradas permite 175 ms/requisicao). Pagina grande: pico de memoria = N requisicoes simultaneas x ate 64 MiB (+copia da resposta); N pode chegar ao tamanho da threadpool (40), ~2,5 GB (calculo, nao medido).

## Correcao recomendada
- Calcular a lista de paginas (nomes ordenados + media type) uma vez no scan e guarda-la (tabela ou campo JSON em `items`), ou cache LRU por `(rel_path, size, mtime_ns)`; `read_page` abre so a entrada pedida e valida o magic dela.
- Limitar concorrencia de leitura de paginas (semaforo, p.ex. 4-8) e/ou tamanho maximo menor por pagina (64 MiB e alto para manga); usar `StreamingResponse` em blocos.

## Correcao aplicada (corretor, working tree)
